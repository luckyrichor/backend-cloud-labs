# 设计取舍

最后更新：2026-10-09；Codex；本轮源码与测量来源统一见 docs/measurements/2026-10-09-fifth-review.json（仓库根目录）；历史章节记录当时结果。

E1 原有 store 单调版本成为缓存判断依据；用 Redis Lua 原子比较版本后写入，拒绝延迟读者的旧版本填充，避免单独 GET/SET 中间被写者插入。Lua 用十进制长度与字符串比较，避免 2^53 以上版本被 double 舍入。

缓存故障时写入 source 已成功，不把缓存失败返回成写失败，否则调用者重试可能重复写。返回 degraded=true。恢复后缓存可能仍有旧值，严格模式读取 source 当前版本，匹配才采用缓存；不匹配直接 source 回退并修复缓存。这牺牲读数据库的减负收益，换来缓存断连、TTL 过期与丢失更新通知后的正确性。此实验明确不把该方案称为高吞吐生产缓存。

生产扩展可引入源存储事务 Outbox、消费版本水位与修复任务，降低逐次验证成本，但需要新增持久源库、消息恢复验证。本次不以没有实测的方案替代严格模式的证据。

source 是内存 store，重启丢数据；Redis 真实集成已验证，但不声称数据库持久性、跨服务写入或完整导购排序。推荐按候选 ID 去重、库存与预算过滤，价格升序、同价 ID 字典序排序。

## 2026-10-08：E3批量过滤与枚举求值

优先采用运算符枚举，将字符串判断从逐文档热路径搬到一次解析阶段；继续递归AST，避免为短路新增跳转/栈语义的字节码复杂度。旧字符串实现只作为冻结基线，不由枚举代码反向生成，差分比较数值与异常。批量API接收只读span并输出值或下标，顺序执行、失败立即终止并给出文档下标；调用者可分块，不隐藏单文档错误或返回难以判断完整性的部分结果。

四模式测量使用同一数据及输出分配策略，轮换顺序，结果完整校验移出计时区。批量API的价值首先是一次解析与清晰过滤契约；是否比调用者自行循环快，要以同批次实测为准，不能把批量接口直接称为向量化提速。规模测量仍是单机合成文档，不推导生产吞吐。


## 2026-10-08：E4被驱逐重排与放置策略组合

保留preempt=spread+抢占兼容，新增preempt-binpack将放置与抢占能力组合；对比必须分别说明收益来自装箱还是驱逐。重排按优先级再尝试空闲节点，不允许重排继续驱逐，从而有界终止；未能恢复的任务显式Pending，历史Preempted不可当作最终失败。Rejected与被驱逐等待区分，离线函数不虚构持续控制循环。

按节点增量维护双资源占用，失败抢占在副本试算、成功才扣除，独立全量重算在所有到达前缀测试中核对。正常选择O(nodes)，抢占与Pending重排仍有扫描成本，不称全流程线性或生产级。E3的批量/枚举只证明本机合成求值优化，索引/线程/列式布局/百亿规模仍未覆盖。


## 2026-10-08：缓存双模式、输入隔离与抢占启发式（Codex）

E1 strict保留正确性默认，cache-first明确返回未校验来源，展示源负载和恢复期陈旧读取的取舍，不把TTL说成严格SLA。E2每连接队列/处理预算隔离洪泛，断线保留30秒后回收身份；代价是到期不能恢复、总帧成本随在线玩家增长，多开连接不受账号配额控制。E4低优先级顺序不变，同优先级优先释放缺口资源，避免小任务先驱逐的已复現用例；两资源贪心不保证全局最优。E3已做枚举和顺序批量，不代表索引、多线程或百亿检索。


## 2026-10-09：接口一致性、局部补偿与可解释对照（Codex）

统一Item snake_case是可见契约变化，Redis切v2键隔离旧格式，避免字段标签不兼容时读成零值。本地失败修复队列保存版本水位，读时强制回源并修复；版本比较防止旧读者清除新失败，溢出保守关闭未校验读。不是持久Outbox，重启和多实例尚依赖TTL/严格模式。

E2对IP限制TCP和保留身份，缓解单主机名额占用而非伪装成账号认证；connected字段明确断线宽限，到期移除需客户端处理。E4分别构造装箱、驱逐、组合场景，组合使用更多驻留资源但驱逐更多，不用一个总分掩盖代价。E3名称绑定到数组slot，共享AST语义，含/不含转换成本两组测量，schema静态缺失与运行期短路缺值分开。

## 第四轮：并发与类型边界（2026-10-09）

E1空队列用原子dirty快速判断；不在nil值接收者中隐式创建队列，避免多个Service副本各自创建、丢失跨请求修复标记。改成cache-first缺队列显式配置错误，在写入前拒绝；NewService/HTTP仍默认启用。标记和overflow不盲目按TTL清理，因为Cache接口无寿命上界、旧回填可刷新TTL，当前保守退化是未解决的可用性限制。需要缓存侧栅栏等协议后再做安全回收。

E2原生IPv6用/64聚合TCP/身份配额，mapped IPv4归一成IPv4，不把IP策略称为账号保证。E3新Bound私有拥有克隆树，只暴露只读evaluate，摆脱调用方“不要重绑”的约定；解析树不暴露Bound内部，构造成本不在热路径。E4按驱逐事件分别累计两类打断资源，拒绝不计入；这是资源量，不是运行进度成本，仍需同时读拒绝、接纳、最终占用。

文档表头只保留更新与统一证据路径，不再手工重复当前基线；历史测量保留当时提交，不用后来的哈希改写历史。第四轮对应元数据2026-10-09-fourth-review.json。

## 第五轮：缓存代际、权威速度与可比较的测量

采用命名空间可达性屏障而非TTL定时遗忘：队列创建生成随机source生命周期prefix；请求捕获固定generation视图再读/写source；溢出切代、清空标记。旧请求填旧代、旧读无法清新标记；旧代请求的源写若跨代完成，哪怕旧缓存填成功也标记当前代。这个写入细节不能靠“换前缀”省略。代际视图prefix在换代时预计算，热路径不逐次格式化代号。代价是新代冷启动、旧条目TTL/内存周期回收、不能共用其他实例的热缓存。本轮不做后台排空或持久Outbox。

推荐并发上限8、输入去重、按下标保存结果/错误、全部worker join后确定排序和错误，避免取消时返回但worker继续写结果。source/cache必须遵循context。E2将32条处理预算与位移预算分开：每帧只采用最新有效意图一次，斜向归一化，seq确认包含被合并输入；这是可见协议语义变更，客户端应每帧提交意图，非逐消息位移累计。

E3数字先按十进制文法扫描，再from_chars转换。字节码跳转短路本来可行；未做VM的理由是尚无与枚举/slot AST匹配输入的性能证据与必要性，不能拿实现复杂度当作技术不可行。当前Bound重新测速且注明构造成本计时外。E1同一源码双开关比较完整Get与内存后端；E4资源需求和打断事件分别累加，不能用同一总分替代代价分析。

旧章节的sticky overflow/不回收为各历史阶段选择；当前能力与限制以status.md和第五轮元数据为准，不覆盖历史源码哈希。

### 2026-10-24 · P1 数据流水线（Claude Code）

负责人在群聊中要求“按方案开始”，视为 CP1 通过：P0 报告列出的回退方案（合成目录、outbox、无监控）均未启用，无需另行确认。

- **Amazon 品类从 1 个补到 3 个**（方案允许 1–3 个）。实测 All_Beauty 只有 15.7% 的行有价格，`categories` 全空、`main_category` 只有 2 个取值，S4 的类目索引几乎无从下推。另下载了三个候选品类做比较：Appliances 有价格 49.5%、叶子类目 92 个；Video_Games 有价格 45.1%、160 个；Health_and_Personal_Care 只有 17.5%，且无类目，弃用。最终选 All_Beauty + Appliances + Video_Games，只保留有标题、价格为正的行，得到 126,367 行公开基底、555 个类目键、22,604 家店铺。不对缺失价格做插补：插补出来的价格分布不是公开数据。
- **类目键用“品类文件:完整路径”**。不同领域的叶子名会重复（如 Accessories），只取叶子会把不相干的类目并成一个。
- **商品目录放大**：第 i 行使用第 (i−1) mod B 行基底。前 B 行是未修改的公开行（库存除外）；之后是克隆行，换新 id、价格扰动 ±5%。全部 200 万行的库存都是合成的，公开数据里没有库存字段。热度是固定种子下的 id 全排列（popularity.u32），loadgen 把 Zipf 排名映射到 id；Zipf 参数 0.99 只是起点，以 loadgen 实际记录的为准。
- **E3 文档**：对公开行有放回重采样，价格扰动 ±2%、评分数扰动 ±5%，评分、类目、店铺原样复制，库存合成。格式为自定义列式二进制 BCLDOC1：定长头部，列按 8 字节对齐，供 C++ 直接读取。不用 Parquet，是为了不给 E3 引入依赖。10^7 档 320 MB。
- **CMDB 图偏离方案“每项约 5 条关系”**。服务依赖出度、入度，以及服务→存储的度分布，取自阿里 MSCallGraph 两个分片的不重复调用对：rpc/http/mq 归为服务依赖，db/mc 归为存储使用；平均出度分别为 3.21 和 6.12。按此分布生成，实际每个配置项约 2.28 条关系。主机与容器的占比是自定的，服务与存储之比沿用阿里数据（约 1:2.98）。要达到 5 条，只能凭空加关系种类或放大度数，两者都没有依据，所以如实保留，并在本节与 status 中标为偏离；是否调整由负责人决定。目标节点按抽样的入度权重选取（Chung–Lu 式），10 个租户等分，关系不跨租户。度数抽样超过可用目标时截断并计数：10^4 档截断 1 次，少 42 条边；更大档为 0。
- **E2 轨迹**：服务端把所有玩家都生成在原点、地图无边界，所以轨迹从原点出发，路点限定在 400×400 范围内，每帧至多 1 单位。每个机器人只使用自己的随机流，64…2000 各档都是同一文件的前缀，不同档之间可以直接比较。热点模式下 80% 的路点落在 4 个热点附近；正态分布用三个均匀数之和近似，以免依赖 Exp/Log 的平台实现。统计中记录了 AOI 半径 25 和 50 内的平均邻居数，供 S3 选取半径时参考。
- **确定性的边界**：同一提交、同一种子、同一输入，在 tx（linux/amd64）上逐字节一致，已用两次独立运行验证。不保证跨架构一致，因为 arm64 上 Go 可能把乘加融合成 FMA。所以正式数据只在 tx 上生成。
- **迁移**：编号的 up/down 文件，配合 schema_migrations 记录校验和；已应用的迁移文件被修改时，拒绝继续执行。MySQL DDL 隐式提交，单个迁移不是原子的，失败时停在出错语句并报告，恢复靠人工。bench_run 仍由 P0 的 init.sh 创建，不纳入迁移，因此全量回滚不会删掉运行登记。roundtrip 命令要求所有被管理的表为空，然后执行全部 down、全部 up，比较 SHOW CREATE TABLE 的指纹。
- **ci 唯一键偏离 D.2**：方案写的是 (tenant_id, kind, name) 唯一，但在时间区间模型下，删除后同名重建会冲突。因此增加存储生成列 live（存在时为 1，删除后为 NULL），唯一键改为 (tenant_id, kind, name, live)。NULL 不参与唯一冲突，所以约束只作用于存活行。已在真实 MySQL 上验证：两条已删除行加一条存活行可以共存，第二条存活行被拒绝。relation 不对 ci 建外键，原因是关系的历史可能早于或晚于 ci 行的重放。
- **商品导入**用多行 INSERT 分事务写入，不用 LOAD DATA LOCAL，以免改动服务器的 local_infile 设置。导入前校验文件哈希与清单一致，导入后核对行数、最大 id、价格总和、库存总和。

### 2026-10-24 · CMDB 关系密度定案（Claude Code）

负责人授权由助手决定。**保持按阿里调用图度分布生成，每个配置项约 2.3 条关系，不补到方案估计的约 5 条。**

- 方案中的“约 5 条”是写方案时没有数据支撑的估计；2.3 来自真实微服务调用图的出度与入度，S7 要讲的是“这类分层依赖图”的性能，形状真实比密度达标更重要。
- 补到 5 条只有两条路：凭空增加关系种类，或者整体放大度数。前者会制造面试时讲不清来源的边，后者会扭曲长尾形状（p99 与最大度数也会被放大）。
- 对 S7 的影响：k 跳查询的扇出比 5 条/项时小，所以绝对延迟偏低。报告里要写明每项关系数，不能把结论外推到更稠密的图。如果 P5 发现图太稀疏、测不出邻接索引的作用，可以用现有的 10^6 档，或者在 P5 内另加一档放大度数的对照组，并标为合成放大；不回头改 P1 的数据。

### 2026-10-24 · P2-1 MySQL 数据源与写令牌（Claude Code）

- **版本递增放在一条语句里**：`INSERT … ON DUPLICATE KEY UPDATE version = LAST_INSERT_ID(items.version + 1)`。这条语句对该 id 加行锁，并发写被串行化，版本不会读后再写而丢更新。`LAST_INSERT_ID(expr)` 让 OK 包直接带回提交后的版本，不用第二次查询，也就没有“查到别人的版本”的窗口。放弃的做法：`SELECT … FOR UPDATE` 再 `UPDATE` 的显式事务，多两次往返，语义相同。实测 16 个并发写者对同一 id 各写 25 次，拿到的版本恰好是 1..400，不重不漏；导入时 9007199254740993 这样大于 2^53 的版本也能精确加一。
- **id 只接受规范十进制**：items.id 是 BIGINT UNSIGNED，如果 `007` 和 `7` 都被接受，就成了同一行的两个名字，缓存键会分裂。非法 id 写返回 400（参数非法）、读返回 404（与不存在一致，不暴露差别）。内存源不受影响。
- **现有测试改用数字 id 并双跑**：方案要求“现有 28 个 E1 测试在适配器下通过”。测试里的 id 机械替换为数字串（如 sku→101、a→1、b→2，保持推荐排序的字典序关系），并新增 catalogtest 工厂，按环境变量选择内存或 MySQL。基准测试仍用内存源，保持历史数字可比。每个测试进程建一个临时库，因为 Go 并行跑各个包的测试进程。
- **写令牌**：方案 B.1 规定 E1 只对写做不记名共享令牌。用 MySQL 源时缺令牌拒绝启动，以免共享数据被匿名改写；内存源默认仍开放，保持原有本地实验与测试契约。

### 2026-10-24 · P2-2 四种读写策略的界定（Claude Code）

- **B 与 D 的界限**：方案把 B 写成“版本门控回填，用于所有回填与写后更新”，把 D 写成“缓存优先（现有 cache_unvalidated）”。现有 cache-first 本身就是门控回填加写后门控更新，如果 B 也这么实现，两组代码完全相同，对照毫无意义。因此 B 定义为不带修复队列的门控缓存优先，D 保持现状（多了本地修复队列与缓存代际）。代价是在无故障负载下，B 与 D 预计没有差别，报告会如实写；两者的差别要靠缓存写失败的故障注入来体现。
- **A 是教科书写法**：未命中时普通 SET 回填，写后 DEL。按方案要求，“这是最常见的写法，不是刻意写差”。竞态用单测确定性地复现：读者取到 v1 后暂停，写者提交 v2 并 DEL，读者恢复后 SET v1，下一次读返回陈旧的 v1。同一时序下 B 拒绝迟到的回填；B 关掉门控后又回到陈旧的 v1；C、D 都返回 v2。这证明 S1 要测的竞态真实存在，也给反向验证提供了一个可以确定判断的例子。
- **反向验证开关只作用于 B**：`GUIDE_UNGATED_FILLS` 配在其他模式上会拒绝启动，以免误配之后得出“门控无效”的结论。
- **观测放在服务外层**：计数器和延迟直方图用包装器实现（observe 包），guide 的策略逻辑里只多了可选的 Tracer 调用。服务端直方图用 HdrHistogram，参数与 loadgen 一致，这样客户端与服务端可以并列报告。原有遥测直方图最小一档就是 0.1 ms，分辨不了 S1 关心的 p99。
- **Redis 的普通 Set 用 MULTI 包住 HSET 与 PEXPIRE**，确保不会留下没有 TTL 的条目。门控脚本仍会与 Set 写入的版本比较。


### 2026-10-26 · S1 的测量门禁与真实 Mac 校准（Codex）

- 预热请求全部完成之后才重置服务端直方图，再建立正式到达时间基准，避免预热慢请求混入正式窗口。代价是两个阶段间有一次管理接口采集间隙，窗口内仍为开环发压。
- 正式请求发完后等足完整的到达窗口，再等待在途请求完成；客户端到达率按固定窗口内实际发出的请求数计算。服务端回源 QPS 的分母记录为采样与排空实际耗时，标为 approximate，不能冒充严格原子窗口。
- 请求失败、缺少正版本、客户端丢到达、直方图溢出、到达率偏离超过 5%、指标采集失败或计数器回退都会标记无效并记录原因。HTTP 200 本身不足以作为有效读；直写 MySQL 必须恰好更新一行。
- 配置先拒绝 NaN、Inf、零请求窗口与超大请求数，避免生成错误统计或不可序列化结果。
- Mac 无需升级 Go：tx 交叉构建 Darwin 发压二进制并标记实际源提交；客户端由真实 Mac 发起，通过临时 SSH 转发到 tx，临时提高当前子进程 nofile。只读校准使用独立故事名 S1-calibration；它没有策略交替、表恢复、写流量及反向验证，不能替代 S1 正式矩阵。


### 2026-10-26 · S1 正式实验的隔离与预先定义口径（Codex）

- 复用固定镜像的 MySQL 实例，但单独建立 `bcl_s1` 数据库；`items_base` 是从已校验哈希的 P1 items.tsv 导入并对账的只读基底，`items` 是实验副本。共享 bcl.items 的初检有 176 行版本不为 1，金额汇总也不同，因此拒绝把它冒充原始基底，保留现状并独立导入。不更新共享 `bcl.items`。复用 MySQL 便于保持与已部署实验相同的 256 MiB buffer pool；代价是基底/活动表共用 buffer pool，报告必须写明，不把结果外推到专用数据库。
- 单独起带 `bcl.experiment=s1` 标签的 Redis 和 E1 容器；固定 CPU Redis=1、E1=2、MySQL=0，内存限制同原部署。只对这台专用 Redis FLUSHDB。每轮停止 E1、恢复上一轮所有尝试写入的 id（包括可能未返回的写），对照基底检查字段相等，然后启动全新 E1。恢复不在测量窗口内；异常退出后控制器首先扫描版本并恢复。
- 固定源码提交、Darwin 发压器和容器镜像修订标签/二进制哈希。真实 Mac 使用持续的临时 SSH 隧道；凭据通过 0600 文件传递，退出清理客户端凭据。每次业务发压之前记录 30 次真实 HTTP 管理请求往返，不把它叫纯链路 RTT。
- 率档规则在探测前写入代码：cache-aside 95:5 分别探测 500/1500/3000 req/s，实验 SLO 是服务端 GET p99 不超过 50 ms（自定义实验阈值，不是产品承诺），取有效且达标的最高已探测率，再取其 25%/50%/80%，向下对齐 50 req/s。没有达标点就停止处理，不擅自缩减矩阵。
- 正式每轮预热 10 秒，测量窗口取 `max(20, ceil(12000/(rate*read_ratio)))` 秒，使预计读样本至少 12000（约 120 个 p99 尾部样本）。同条件各组同窗口；种子由重复编号决定，所有策略重放相同请求计划。五次重复，奇数 A/B/C/D、偶数 D/C/B/A，避免只跑完 A 再跑 B。额外的 A/B-off/B 反向组、A/B/C/D 直写 MySQL 组在高率 95:5 条件下各重复五次，正反顺序交替。
- 陈旧读仍采用同一客户端单调时钟上“请求发送前已收到成功写确认的最大版本”这个保守下界。它不依赖跨机时钟，但无法统计提交后、确认前的窗口；不得冒充方案中所有已提交版本的精确陈旧率。对单热点保留服务端单调时间线辅助解释。


S1 编排联调补充：实际 Mac SSH 客户端约 1024 通道时报 poll: Invalid argument，采样期间服务容器仍健康，因此将当前发压器上限固定为 256，额外只读预建 128 个 HTTP 连接，避免正式热身混入连接启动风暴。这个预建步骤不写商品，不进入客户端窗口、服务端直方图或版本真值日志；对所有策略一致。实际是否解决链路抖动须以后续证据为准。不能将 SSH 故障误报为业务服务容量上限，也不能放宽有效性门禁来取得“完成”的矩阵。


S1 先导矩阵后的采样范围更正：正式 scheduled/reads/writes 与 dropped 必须同一窗口。预热本来丢弃，因此新增 warmup_dropped 显式记录，不混入正式丢失；预热已发出请求若失败仍判无效，源写审计必须通过。旧结果保持原样，新源重新执行矩阵，避免事后修改 valid。发压连接上限 384、只读预建 128 个不同热度键，所有策略一致。
