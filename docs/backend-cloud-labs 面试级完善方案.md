# backend-cloud-labs 面试级完善方案

Oct 19, 2026 · @sh6\_apple

本方案把 backend-cloud-labs 从“功能能跑”推进到“有真实数据量、有部署、有压测报告、有可复现的优化故事”：5 个实验各出至少 1 条故事，共 7 条，E1 占 2 条。读者是接手开发的 AI Agent。

**标注约定。** 全文用 \[事实\]（已核对来源或实测）、\[推断\]（据事实推理）、\[未核实\]（尚未验证）三种标签；无标签的句子是要求。

### A.2 指标定义（全文唯一定义处）

- **延迟分位数**：压测程序用 HdrHistogram 记录，采用开环（固定到达率）发压，避免协调遗漏；同时记录服务端自测直方图，两者并列报告。Mac 到 tx 的网络往返包含在客户端侧数字里，报告中写明。
- **成功率**：HTTP 2xx（或协议成功应答）占发出请求的比例，超时记为失败。
- **陈旧读（E1）**：读到的版本小于“该读开始时刻之前已提交的最大版本”。真值来自写入端的提交日志（商品 id、版本、提交时间）。
- **不一致窗口（E1）**：某版本在 MySQL 提交到缓存首次返回该版本的时间差。
- **超时帧（E2）**：单帧处理耗时超过帧间隔（50 ms）；“稳定”判据为超时帧占比低于 1% 且无因服务端过载导致的断线。该判据是定义，不是预测值。
- **数据正确性**：优化前后同一输入的输出必须逐位一致（E3 命中集、E4 放置决策、E5 图查询结果）；不一致即为缺陷，不进入性能对比。

### A.3 数字纪律

1. 方案不预写“预计提升 XX%”。每条故事先写“预期会发生什么、为什么”，实验后对照。
2. 提升不超过 10% 的结果一律记为“无显著提升”。
3. 同条件至少重复 5 次，报告中位数与范围（最小到最大）；A/B 交替运行以抵消漂移。
4. 没有原始结果文件的数字不进报告。每个指标对应：原始结果文件、可重跑脚本、固定版本数据（含校验值）、环境记录（提交号、镜像摘要、机器规格）。
5. 公开数据集的结果称“离线评测数据/压测数据结果”，不称线上生产数据；模型桩不涉及（见 B.4）。
6. 报告中事实、推断、未核实分开写。

### B.2 部署与运行约束

- 仓库现有规则延续：Docker 默认跑在 tx；代码必须先同步并校验哈希再测试（通过 workplan-docs/scripts/run-on-tx.sh）。
- 现有三个服务都只监听 127.0.0.1，容器化后监听地址必须可配置，默认值保持不变。
- E2 有每 IP 连接配额与 128 个身份上限；Mac 上的压测程序所有机器人来自同一个 IP，会被拒绝。这两个限制要改为可配置，默认值与现有行为契约一致，压测时显式调高并在报告中记录。
- tx 只有 4 核且 MySQL、Redis、被测服务同机，互相挤压。每个容器用 cpuset 固定核心，压测实验串行运行，实验间清理页缓存与数据库状态。
- Prometheus 与 Grafana 尽量部署：核心栈（MySQL、Redis、服务）先起，空载下 tx 开始使用 swap，即认定内存不足，跳过这两个组件。跳过时的回退方案：服务端保留指标端点与 pprof，压测程序把直方图与系统采样写入结果文件，前端控制台的报告页读文件绘图；该决定记入设计决策文档。

### B.3 压测程序位置与可信度

- 压测程序为新增的独立 Go 模块 loadgen，在 Mac 上运行，支持 HTTP（E1、E5）与 E2 的 TCP 行 JSON 协议两类负载。
- E3 的性能数字来自 tx 上的进程内基准程序，E4 来自 tx 上的离线重放程序，两者不经过 Mac 网络。压测程序只用于 E1、E2、E5 的网络服务。
- Mac 到 tx 的往返抖动会掩盖毫秒级差异。每组实验开始前记录 Mac 到 tx 的空载往返分布，报告以服务端直方图为主、客户端直方图为端到端参考。抖动大到使同条件重复的范围宽于两组差距时，结论记为“无显著提升”并补一组把压测程序放在 tx 上的对照运行，仅用于校准，不作为主结果。

### B.4 模型调用、密钥与模型桩

- 本方案的 7 条故事都不调用大模型，因此不设模型调用预算，也不需要模型桩；“真实模型与模型桩分工”不适用。报告中不出现任何模型桩数字。
- 项目级已有腾讯云与火山引擎两个模型 API Key，用户已测试可调用（\[事实\]，用户说明）。本方案不使用它们；若后续引入模型调用，密钥只放 gitignore 的 .local/ 目录，不进仓库、不进对话、不进日志，并先补充模型桩与预算章节。

### B.5 密钥与机密管理

- 数据库口令、JWT 签名密钥、服务间令牌都由部署脚本在 tx 上生成并写入 gitignore 的 .local/ 或容器环境文件，仓库只留示例模板。

- 任何需要用户登录或授权的数据集，由用户在本机完成授权或下载，不在对话里粘贴口令或令牌。

### C.2 选型与理由

- **MySQL 8（容器）**：岗位 06 要求 MySQL；ROW 格式 binlog 提供完整行镜像，其中的行版本可直接供 Redis 侧“只接受更新版本”的脚本使用，这也是 S2 能处理乱序的原因。
- **Redis + Redis Stream（不装 Kafka）**：用户决定。Stream 的消费组提供确认与重试；tx 只有 7.5 GB 内存，Kafka 与 MySQL、Redis 同机不合适（\[推断\]）。取舍记入设计决策文档：Stream 无分区、单机，不声称具备 Kafka 的扩展性。
- **binlog 读取**：优先使用 Go 社区库 go-mysql-org/go-mysql 的 canal 模块。对 MySQL 8 默认认证方式的兼容性 \[未核实\]；由 Phase 0 的验证任务确认。回退：改用同事务写入的 outbox 表轮询，并在报告中如实说明 S2 已不是 binlog 方案。
- **loadgen 用 Go（HdrHistogram）**：与被测服务同语言，跨平台编译到 macOS 简单；开环发压自写。
- **E3 继续用 C++，索引与 VM 也写在 E3 内**：岗位 15 要求 C++，且 ExprTk 同为 C++ 头文件，比较公平。
- **E3 字节码 VM**：用户决定加入。这推翻了仓库之前“不做 VM”的设计决策，记入 docs/design-decisions.md（原因：需要在面试中能说清 AST 与 VM 的取舍；代价：多一套求值路径需要维护）。
- **前端 React + TypeScript（Vite 构建）**：用户指定。控制台直接调用各服务的 HTTP 接口（服务端配置 CORS），不再新增网关层；图表库、状态管理库由 Agent 选择并记入设计决策。
- **Prometheus + Grafana**：见 B.2 的跳过规则。
- **鉴权**：E5 做完整 RBAC 与租户隔离，对应岗位 17 的“权限”要求；E1、E2 只做不记名的共享令牌鉴权（写接口、加入房间），避免重复造轮子。

## D. 数据设计

数据分三类：关系型业务表（MySQL 8）、压测与结果登记表、由脚本生成的列式/二进制评测文件。原始公开数据不进仓库，仓库只留下载脚本、清单（地址、大小、校验和、行数）与统计结果，数据落在 tx 的仓库外目录。

### D.1 设计原则

1. **版本即真相。** 所有可缓存、可回放的实体带单调递增的 version，由数据库在同一事务内递增；缓存、事件、审计都只比较版本，不比较时间。这沿用 E1 现有契约（大于 2^53 的版本仍用十进制字符串比较）。
2. **事件先于视图。** E5 的状态由追加变更事件推出，快照和内存邻接索引都是可丢弃、可重建的加速结构。
3. **索引服务于已列出的查询。** 每个索引都对应 E 章里一条具体查询或写路径；没有对应查询不建，且必须能“删掉索引”做反向验证。
4. **生成可确定、可重建。** 合成数据全由固定随机种子与生成器版本决定；“数据版本”= 清单哈希 + 生成器 commit + 种子，写入每条结果记录。
5. **真实与合成分开标注。** 每个数据文件与结果记录都带 source=public|synthetic 与放大倍数；报告里不把合成部分的结论说成公开数据的结论。

### D.2 表结构与索引（MySQL 8，utf8mb4，InnoDB）

| 表 | 用途 | 关键列 | 索引（对应的查询） |

### D.3 数据规模目标

| 对象 | 公开基底 | 目标规模 | 放大方式 |

### D.4 放大方法与局限

- **商品目录放大。** 克隆行共享同一价格与类目联合分布，但不保留真实商品之间的相关性（同店、同系列）；访问热度是合成的 Zipf，参数写入清单，不声称贴近真实流量。
- **索引测试的选择率。** S4 的规则集按选择率分档设计（从极低到近一半命中），选择率由生成后的数据实测计算，不靠猜。数据来自商品属性，不代表广告/风控真实规则分布。
- **图放大。** 合成图的度分布形状来自公开图、分层与租户结构是自定的；结论只适用于这类分层依赖图，不推广到真实 CMDB。
- **规模上限。** S4 最大 10^7 文档，远低于岗位 15 提到的百亿量级。报告只报 10^7 以下的实测，分片扩展只写成“推断”。
- **原始数据存放。** 公开数据落在 tx 仓库外的数据目录；仓库 datasets/manifest.json 记录地址、大小、校验和、行数、许可原文链接；datasets/stats/ 保存统计结果（行数、分布直方图）。

## E. 优化故事

七条故事共用下面的实验规程，每条只写各自独有的部分。“预期”写的是方向与原因，不写百分比；跑完后在报告里对照，预期被推翻也如实记录。

### E.0 通用实验规程

- **对照运行。** 基线与改动版用同一仓库提交、同一数据版本、同一机器，仅用一个配置开关切换（基线代码不删，作为可选策略保留）；A、B 交替运行至少 5 轮，每轮先预热（丢弃）再取稳定窗口，窗口长度在设计决策文档中按“直方图足够填满 p99”取定。
- **定位。** 先看服务端直方图与 pprof（CPU、锁等待），再决定改动；每条故事的“定位”一格必须给出证据文件路径，没有定位证据的故事不算完成。
- **反向验证。** 把优化用开关关掉，重跑同一组条件，指标必须回到基线范围内；回不去说明收益来自别的因素，故事不成立，必须查清原因再重做。
- **正确性门禁。** 任何性能对比之前，两组输出必须按 A.2 “数据正确性”一致。

### S1 · E1：真实慢源下的缓存读写策略对照

| 项 | 内容 |
| --- | --- |
| 问题 | 现有 E1 的源与缓存都在进程内，“缓存优先”没有任何收益（\[事实\]，现有基准见附录 A），一致性策略没有在真实数据库前经过验证。常见的“写后删缓存”在并发读写下会把旧值回填进缓存（\[推断\]，需要实测确认） |
| 基线 | cache-aside：读先查 Redis，未命中查 MySQL 再用普通 SET 回填，TTL 1 分钟；写 MySQL 后删除 Redis 键。这是最常见的写法，不是刻意写差 |
| 对照组 | B 版本门控回填（现有 Lua “只接受更新版本”脚本用于所有回填与写后更新）；C 严格校验（每次读都先取 MySQL 的 version）；D 缓存优先（现有 cache\_unvalidated）。四组同条件对照 |
| 定位方法 | 对一条热点 key 记录“读开始、MySQL 返回、回填、写提交、删除”的时间序列，确认混入旧值的竞态确实发生；用直方图确认 C 组延迟下限等于 MySQL 点查延迟 |
| 预期及原因 | A 组在热点键上读写并发时会出现一批陈旧读，持续到 TTL 或下一次写；B 组把这类竞态导致的陈旧读大幅减少。C 组陈旧读最少，但每次读都要一次 MySQL 往返，MySQL QPS 与读 QPS 同量级。D 组延迟最低，但直接写 MySQL 的写入（绕过本服务）会留下长期陈旧值。以上都是推断，结论以实测为准 |
| 改动 | 在 E1 内把读写策略抽成可配置的四种；MySQL 适配器实现现有 source 接口（版本由 UPDATE 在同一事务内递增）；写接口返回提交版本供压测程序建立“真值日志” |
| 对照实验 | 工作负载：200 万商品，读访问按 Zipf，读写比 95:5 与 99:1 两档，写也按同一 Zipf 落在热点上；三个到达率档（由基线空载延迟与 SLO 定义出）。四组 × 两档读写比 × 三个率 × 5 次重复。写入走服务接口，另设一组“绕过服务直写 MySQL”单独报告 |
| 指标 | GET p50/p95/p99（客户端与服务端）、陈旧读比例、MySQL 读 QPS、Redis 命中率、成功率 |
| 代价 | B 的 Lua 脚本与每次回填的额外 Redis 操作；C 的 MySQL 压力；D 的陈旧风险。报告必须列出这些代价，不只列收益 |
| 反向验证 | 把 B 的版本门控关掉（回填改普通 SET），陈旧读比例应回到 A 组范围；若没回去，说明 A、B 的差异不来自版本门控 |

### S2 · E1：跨实例不一致窗口（binlog + Redis Stream）

| 项 | 内容 |
| --- | --- |
| 问题 | 服务开两个实例、各有进程内缓存时，一个实例的写入不能让另一实例的本地缓存失效，现有契约也明确“不声称多实例一致性”（\[事实\]，E1 api.md） |
| 基线 | A：写路径只删本实例本地缓存与 Redis，其他实例靠本地 TTL 过期；B：在 A 基础上写后延迟再删一次（延迟值由 Phase 2 实测的 MySQL 读 p99 决定，记入设计决策） |
| 改动 | C：独立进程读 MySQL ROW binlog，把“商品 id、新版本”事件写入 Redis Stream；每个服务实例用自己的消费组读取，按“只接受更新版本”的规则失效或更新本地与 Redis 缓存；确认后才 ACK，崩溃重启从未确认位置继续，重复与乱序事件无害 |
| 定位方法 | 散点审计：压测程序在实例 A 写、同时以固定间隔轮询实例 B 的读，记录 B 首次返回新版本的时刻，确认基线窗口贴近本地 TTL。写、读的时刻都由 Mac 上同一个压测进程给出，避免跨机器时钟漂移；轮询间隔决定窗口测量的分辨率，不能小于该间隔的结论不下 |
| 预期及原因 | A 组窗口按本地 TTL 的量级分布；B 组压缩了窗口，但没有解决“延迟值设置不对”“删除失败”的情况；C 组窗口约等于 binlog 读取、写 Stream、消费三段延迟之和，远小于 TTL。故障注入（消费者停止若干秒、事件重放、乱序）后 C 组最终应全部收敛，而 A、B 组依赖 TTL。都是推断 |
| 对照实验 | 三组 × 写速率三档 × 5 次重复。另设故障用例：消费者停止 N 秒后恢复、人为重复和乱序投递事件，记录收敛率和收敛耗时 |
| 指标 | 不一致窗口 p50/p99、binlog→Stream→应用两段事件延迟、故障后最终收敛率、写接口 p99（不应变差）、成功率 |
| 代价 | 多一个独立进程和一条消息通道；binlog 与主库权限要求；Stream 无分区，单机，不声称 Kafka 级扩展性；消息丢失或积压时需要全量重建以外的兜底（相对于 TTL 到期）要写清楚 |
| 反向验证 | 停掉 binlog 消费进程，窗口应回到 A 组的量级；再启动后收敛率回到完全收敛 |

### S3 · E2：大房间下的快照成本（AOI + 增量）

| 项 | 内容 |
| --- | --- |
| 问题 | 每帧向所有玩家广播完整快照，单帧下行总字节随人数的平方增长（\[推断\]），现有上限 128 人掩盖了这个问题；快照队列仅 4 条，慢客户端会被断开（\[事实\]，E2 README） |
| 基线 | 现有实现：50 ms 一帧，所有人收同一份完整 JSON 快照。为压测把 128 人上限、每 IP 配额改为可配置（见 B.2），默认不变 |
| 定位方法 | 服务端记录帧耗时直方图、每帧序列化字节数、写队列满导致的断开次数；pprof 确认帧内时间主要花在序列化、写套接字还是状态计算。把“超时帧”开始出现的人数记为基线拐点 |
| 改动 | 网格空间索引，每个客户端只收半径 R 内的玩家（AOI）；在 AOI 基础上发送相对上一次已发送状态的增量（进入、离开、变化的字段），客户端序号断档或重连时补发全量。新协议由客户端在 join 时声明能力才启用，默认行为和现有契约一致（见附录 B） |
| 预期及原因 | 两种轨迹下结果不同。“均匀随机路点”下每人可见数远小于总人数，下行字节明显下降；“热点聚集”下大家都能看见彼此，AOI 基本不减少字节，还因为每客户端单独序列化增加 CPU，帧耗时可能反而变差。这两个结果都要报告，不得只报好的那个。以上都是推断 |
| 对照实验 | 在线机器人数档（64、128、500、1000、2000）× 轨迹两种 × 两个组（全量快照、AOI+增量）× 5 次重复。机器人由 Mac 上的压测程序发起，连接数需要的句柄上限在两端都要检查（tx 侧见 B.1） |
| 指标 | 帧耗时 p50/p95/p99、超时帧占比、每客户端每秒下行字节、因过载被断开的连接数、“超时帧占比低于 1%”的最大在线人数（定义见 A.2） |
| 正确性 | 客户端用快照加增量重建的视图，与服务端在同一帧的权威状态过滤后的结果逐帧一致（采样检查）；现有测试和现有护栏（每帧一次移动、断线宽限、连接身份检查）不得回归 |
| 代价 | 协议和状态机更复杂；服务端需要为每个客户端保存上一次已发送状态；视野外的玩家看不到，产品上要明确这是设计选择 |
| 反向验证 | 把 AOI 半径调到覆盖全房间、关闭增量开关，字节数与帧耗时回到基线范围 |

### S4 · E3：规则到索引条件下推

| 项 | 内容 |
| --- | --- |
| 问题 | 现有 E3 只能对每个文档逐个求值，最大实测 10 万文档（\[事实\]，现状文档），延迟随文档数线性增长（\[推断\]，需实测确认）；岗位 15 需要的是“规则 + 检索”，而不只是求值 |
| 基线 | 现有查询路径：按槽绑定后对列式文档数组顺序求值。这已经是一个合理的高效全扫描，不是刻意写差 |
| 定位方法 | 用 10^5、10^6、10^7 三档文档数测查询延迟，确认线性增长；用 perf 确认时间花在求值器还是内存读取 |
| 改动 | 从规则的 AST 中抽取形如“列 比较运算 常量”的合取条件，用有序列索引（范围）、等值倒排（类目、店铺）得到候选文档集合；选择性最高的条件优先，多条件取交集；含 OR 或 NOT 的子条件首版不下推（其所在合取项只用于残余求值）。对候选集重新求值完整规则后才返回结果（安全优先）。选择率很高时规划器退回全扫。首版文档集只读，不支持增量更新 |
| 预期及原因 | 选择率低的规则，延迟由“候选数”决定，远小于全扫。选择率接近一半的规则，交集与回查的开销会抵消索引带来的节省，可能没有收益甚至变慢，这也是规划器要解决的对象。以上是推断 |
| 对照实验 | 20 条规则模板，选择率分档从极低到近一半，选择率由实际数据统计得到；三档文档数 × 两组（全扫、下推）× 5 轮。单线程测量（先不引入并行变量）。独立参照：同一文档与同一规则用 ExprTk 全扫，避免只与自己的基线对比 |
| 指标 | 每条规则的查询延迟 p50/p95/p99（重复执行汇总）、候选文档比例、索引构建耗时与大小 |
| 正确性 | 下推结果与全扫结果的命中文档集合逐条相等；附加随机规则差分测试。现有 4 项 CTest 与现有语法、短路、错误契约不变 |
| 代价 | 索引构建时间与大小、数据变更后索引重建、规划器误判的风险；不支持增量更新必须在报告中写明 |
| 反向验证 | 用开关禁用下推（强制全扫），延迟回到全扫范围 |

| 预期及原因 | 逐文档的 B 相对现有 AST 可能没有显著差异：规则很小、节点少、现有路径已是枚举加 switch。成组批量的 C 减少逐文档的解释开销，更有可能拉开差距。这是推断，“无显著提升”是完全可接受的结论，需要如实写下来 |
| 对照实验 | 同 S4 的规则集与文档，全扫模式，单线程，4 组交替运行，每组 5 轮 |
| 指标 | 每文档求值耗时、每秒文档数，按规则复杂度（节点数）分层报告 |
| 正确性 | AST、VM、批量 VM、ExprTk 四路在随机规则 × 随机文档上差分；错误语义（除零、非有限结果报错、短路跳过的分支不报错、错误带文档下标）与现有契约一致。ExprTk 的语法与本引擎不同（例如不支持 &&，要写 and），参照规则按各自语法逐条翻译后，只比较命中集合与耗时。 |

| 反向验证 | 用开关切回 AST 路径，指标回到基线范围 |

### S6 · E4：用公开轨迹检验调度策略，并消除全节点扫描

| 项 | 内容 |
| --- | --- |
| 问题 | 现有评测只服务自写的 12 行场景，“自己出题自己答”（\[事实\]，status.md）；每次放置扫描节点，抢占候选扫描驻留任务并排序，每次到达都重扫 Pending（\[事实\]，E4 README），节点数上去以后决策延迟会变差（\[推断\]） |
| 基线 | 现有调度函数在轨迹重放下运行：全节点线性扫描。重放器需要“任务结束”事件来释放资源，现有实现没有（\[事实\]），需新增释放接口且不破坏现有契约 |
| 改动 | 1）轨迹导入与重放器。轨迹语义以数据集页面为准：priority 0 为高、1 为低且可能被提前驱逐；endtime 为空表示超过 90 天上限；starttime 为负表示采集开始时已存在；资源是机型容量的分数（\[事实\]，来自该数据集的说明页）。vmType 表中“同一机型的分数如何映射到节点”的细节 \[未核实\]，第 4 阶段的第一个任务是读数据并把一份“语义笔记”写进设计决策文档；2）按剩余容量分桶的节点索引，用于 spread 与 binpack 选节点；3）输出指标 |
| 定位方法 | 节点数 10^2、10^3、10^4、10^5 四档下测放置决策延迟，确认随节点数增长；pprof 确认时间花在节点扫描。策略对比部分用同一轨迹片段、同一节点规模跑 spread、binpack、preempt、preempt-binpack |
| 预期及原因 | 索引在 100 个节点下基本没有收益（维护索引的开销与扫描相当），在万级以上节点开始拉开差距；preempt 路径的驱逐候选排序不受该索引影响，改进有限。策略对比方面，我预期 binpack 在低负载时节点占用更集中，preempt 类策略降低高优先拒绝率但增加驱逐次数。这些都是推断 |
| 对照实验 | 决策延迟：四档节点数 × 两组（线性扫描、分桶索引）× 5 轮。策略质量：四种策略在同一轨迹片段、同一节点规模上各跑 5 轮（重放本身确定，轮间差异只来自计时，质量指标各轮应完全一致，不一致即为不确定性缺陷） |
| 指标 | 决策延迟 p50/p95/p99（每次 Schedule 调用，墙钟时间）、高优先拒绝率、低优先驱逐次数、资源利用率、资源碎片（空闲但放不下最小机型的容量占比） |
| 正确性 | 索引组与扫描组对同一轨迹的逐条放置决策完全一致（包括平局按节点输入顺序的规则）；每个节点任一时刻的资源不超容量（独立重算，不用增量账本自证）；每个请求 ID 只处于驻留、拒绝、等待、已结束之一 |
| 代价 | 索引维护开销与代码复杂度；二维资源（CPU、内存）下分桶索引的精度取舍要在设计决策里写清；轨迹重放不是在线调度器，无控制循环、无弹性扩缩容，这一点必须在报告中写明（岗位 16 关注弹性伸缩，本故事不覆盖，见 G） |
| 反向验证 | 用开关切回线性扫描，延迟回到基线范围 |

### S7 · E5：变更落盘、邻接索引与历史查询

| 项 | 内容 |
| --- | --- |
| 问题 | 现有实现每次变更都克隆整个状态并把整个图加前后快照重写到一个 JSON 文件；关系是切片，遍历每个节点都扫全部关系，删除关系线性找位置（\[事实\]，store.go 中的克隆、关系切片与遍历循环，对应 b98f225）。图与历史一大，变更延迟与文件大小都会随规模增长（\[推断\]） |
| 基线 | 现有文件存储实现，保留为可选策略。基线的规模上限如果在某一档上跑不完（如历史文件超过磁盘或驱动超时），该档记“基线无法完成”并附原因，不调低规模伪造对比 |
| 改动 | 三个独立开关，分别做对照：① 落盘：每次变更在一个 MySQL 事务里追加一条 change\_event，周期写快照文件登记到 snapshot\_meta；② 遍历：启动时由 relation 表加载内存邻接索引（正向与反向），变更同步维护；③ 历史：用 created\_rev/deleted\_rev 区间判断“在 rev N 时存在”，从最近快照加事件重放得到任意历史版本。审计记录仍带前后变化，但由事件推导而不是存整图快照 |
| 定位方法 | 图规模三档（10^4、10^5、10^6 配置项）测变更延迟、历史文件大小、遍历延迟，确认随规模增长的关系；pprof 确认用于克隆、序列化、写盘与扫描各占多少 |
| 预期及原因 | 变更延迟从“随图大小增长”变为“基本与图大小无关”，因为每次只写增量；但 MySQL 事务提交本身有固定开销，在小图上可能反而比写本地文件慢。邻接索引让遍历延迟从“随全部关系数线性增长”变为“随访问到的边数增长”。重启恢复时间取决于快照间隔。以上都是推断 |
| 对照实验 | 三档图规模 × 每个开关 × 两组 × 5 轮。遍历用固定的 1000 个起点、深度 1–5、三个方向。还要做崩溃恢复用例：写压下用 kill -9 杀进程并重启，检查“已确认的变更一条不丢、未确认的变更不会凭空出现” |
| 指标 | 变更写延迟 p50/p99、每次变更的写入字节数、遍历延迟 p50/p99、历史时点查询延迟、重启恢复耗时、历史存储大小随变更数的增长 |
| 正确性 | 同一变更序列下，新旧实现在任意 rev 的图、遍历结果、审计内容逐项一致；重启后状态与重启前一致；20 并发 CAS 、删除有关联项被拒绝等现有契约不变（见附录 A） |
| 代价 | 对 MySQL 的依赖；内存邻接索引和快照重建逻辑的复杂度；单进程仍然是单点，不声称多实例。全局版本 CAS 仍会让无关写入互相冲突（现有取舍），按租户拆分版本号是可选的跨版本改动，不在本故事范围 |
| 反向验证 | 分别关闭三个开关，对应指标回到基线范围 |

### A.4 不能破坏的行为契约

- **E1**：Item 响应字段 id、title、price\_cent、stock、version、updated\_at；GET 的 source 取值 store / cache\_validated / cache\_unvalidated；写的线性化点在 source Put；写后缓存失败仍返回 200 且 degraded=true；PUT 没有幂等 key；未知字段、尾随 JSON、超 1 MB、参数非法返回 400，不存在返回 404，源故障返回 503；推荐去重、忽略不存在候选、库存>0 且价格不超预算、价格升序同价按 ID 字典序、最多 8 路并发；默认 strict。
- **E2**：每帧每玩家只应用最新一次移动意图，斜向总长度不超过 1；seq 递增且同号或旧号不重复移动；重连后旧连接输入一律作废；握手 5 秒、输入空闲 30 秒、写 2 秒、单行 64 KiB、每连接输入队列 64 与快照队列 4、每帧最多消费 32 条；身份上限 128、同 IP 最多 16 个连接与 16 个身份、全局 256 个连接（IPv6 按 /64）；断线保留 30 秒后原 token 失效。这些数值在可配置化后默认值不变。
- **E3**：十进制数字文法（digits\[.digits\] 或 .digits，可带 e/E 指数，拒绝十六进制、残缺指数、溢出、非有限数）；输入 4096 字符、AST 256 节点、嵌套 64 层；&& 与 || 短路；未知变量、除零、非法语法报错；批量错误带从 0 开始的文档下标且不提供部分结果；槽位求值只检查实际访问的槽，短路跳过的缺失或非法值不报错；Bound 拥有自己的只读树。
- **E4**：每个输入 ID 恰好处于驻留、拒绝、等待之一；节点资源不超容量；失败的抢占不修改账本；只驱逐严格低优先级任务；重排只用空闲资源、不再抢占；结果由输入顺序确定。
- **E5**：以 expected\_revision 对全图做 CAS；actor 与 reason 必填；删除仍有关联的配置项被拒绝并要求显式解绑；间接环允许且遍历不死循环；图查询深度 0–10、返回访问节点的诱导子图、稳定排序；审计 limit 1–100；历史快照不被后续更新覆盖；重启校验版本连续性与快照链。引入鉴权后，actor 改由登录身份填充，这是可见契约变化，需记入 design-decisions。

### B.5 关键业务流程

1. **E1 写入与失效（S2）**：写请求到达实例 A → 事务内更新 MySQL 并递增版本 → 返回提交版本 → binlog 读取进程把“商品 id、新版本”写入 Stream → 每个实例的消费组读取并按版本失效或更新本地与 Redis 缓存 → 确认。任一环节崩溃后都能从未确认位置继续。
2. **E5 变更**：客户端带令牌与 expected\_revision 提交 → 鉴权与租户校验 → 校验输入 → CAS 判断 → 同一事务内追加变更事件并更新关系表 → 同步更新内存邻接索引 → 返回新 rev。让内存状态在落盘成功之后可见，不暴露未持久化的状态。
3. **一次完整压测运行**：登记 bench\_run → 检查工作区干净与数据版本 → 预热（丢弃）→ 稳定窗口采样 → 写原始结果文件与环境记录 → 正确性门禁 → 完成 → 跨次汇总并自动判定结论标记。
4. **E3 规则试验**：校验规则（语法与限制）→ 生成执行计划（是否下推）→ 执行 → 返回计划、候选数、命中数、耗时。

### B.6 通用约定

- **幂等**：E1 的 PUT 维持现状（无幂等 key，不自动重试未知结果）。E5 的变更靠 expected\_revision 天然防重复；另加可选的 request\_id，使同一 request\_id 与相同内容的重试返回原结果，内容不同则拒绝。
- **错误码**：沿用 HTTP 状态语义——400 参数非法、401 未登录、403 无权限、404 不存在（含跨租户）、409 版本冲突、429 限流、503 依赖故障；响应体带机器可读的 code 与人可读的 message。E1 现有的 400/404/503 映射不变。
- **分页**：沿用 E5 审计现有的 offset 与 limit（limit 1–100），其他列表接口用同一套。
- **金额**：一律整数分（字段名以 \_cent 结尾），不用浮点数。
- **时间**：存储与接口一律 UTC，RFC 3339 带毫秒以上精度；控制台按浏览器本地时区显示，并在报告页标明时区。
- **64 位版本号**：新增接口里一律用十进制字符串（避免大于 2^53 的精度丢失），现有 E1 字段保持原样。
- **鉴权与跨域**：Authorization: Bearer 令牌；控制台来源列入服务端白名单；请求带 X-Request-Id 并写入日志。
