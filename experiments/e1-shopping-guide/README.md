# E1 导购服务 + 缓存一致性

对应岗位 **06（字节 后端开发-导购方向）**。排期见 `workplan-docs/总节奏表.md`：W3 主力档，预估 5 h。

**当前状态：骨架就位，实验本身尚未开始。**（2026-09-20）

## 这个实验要回答什么

一个能复现、也能解决的具体问题：**缓存与数据库在并发读写下不一致**。

不做成一个"带缓存的商品服务"就算完 —— 那样只能讲"我用了 Redis"。要能讲清楚：不一致是怎么产生的、为什么选这个写策略而不是另一个、缓存挂掉时怎么降级。

## 已经做了什么

| | |
|---|---|
| Go module | `go 1.27`，零第三方依赖 |
| `internal/catalog` | Item 模型 + Store 接口 + 内存实现，5 个测试，`-race` 通过 |

两个刻意的设计选择，后面的实验都建立在它们之上：

- **Item 带单调递增的 `Version`**，由 store 自己分配，调用方传什么都会被忽略。有了它，"缓存里这份是不是旧的"是个可判定的问题，不用去比时间戳、也不受时钟偏移影响。
- **缓存不放在 `catalog` 包里面**。一个自己偷偷缓存读结果的 store 会让不一致变得不可观察，而这个实验的全部意义就是让它可观察。

## 还没做的部分

缓存层、HTTP 接口、降级路径、一致性的复现与验证 —— 也就是这个实验的正题，全都还没开始。**不要把当前状态描述成"导购服务已完成"。**
